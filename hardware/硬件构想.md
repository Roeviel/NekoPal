### 0.1 四个拍板

| # | 问题 | 结论 | 影响 |
|---|---|---|---|
| 1 | 主控架构 | **双脑**：ESP32-S3（实时）+ Pi Zero 2 W（交互） | 见 §0.2 |

### 0.2 为什么要"双脑"

需求里有两类**互相冲突**的东西：

| 需求 | 要的是 |
|---|---|
| 屏幕表情（≥30fps）、录音与语音前端 | **吞吐**（持续刷屏 + 音频编解码） |
| 急停、防跌落、编码器闭环、回充对接 | **确定性**（晚 50ms 就是撞墙或掉下桌子） |

单靠一颗 ESP32-S3：显示屏 + WiFi + 音频同时跑，**PSRAM 带宽和 CPU 会被吃光**，
运动控制环就会被挤到抖动 —— 这恰恰是最不能抖的地方。

单靠一块树莓派：Linux 的调度抖动让电机闭环和急停**不可靠**，而它还不省电。

所以：

```
┌──────────────────────────────────────────────┐
│  实时脑  ESP32-S3                             │
│  电机闭环 1kHz · 编码器 · IMU · ToF · 防跌落    │
│  硬线急停 · 电源管理 · 回充对接                  │
│  —— 只做确定性的事，永远不被屏幕上的一帧卡住      │
└───────────────┬──────────────────────────────┘
                │ UART（NDJSON+CRC32，见 PROTOCOL.md）+ 一条硬线急停
┌───────────────▼──────────────────────────────┐
│  交互脑  Raspberry Pi Zero 2 W                │
│  圆形屏表情 · 麦克风 · 功放喇叭                 │
│  WiFi 连蕴（对话/指令/设备控制）+ 网关进程       │
└──────────────────────────────────────────────┘
```

**关键**：急停走**硬线**，不经过 UART。交互脑死机、UART 堵塞，实时脑照样能停。

│   │ 防跌落红外 ×2（朝下）             │R  │ 网关进程（HTTP :8791） │ │
│   │ IR 接收 ×3（回充引导）            │T  │ WiFi → 蕴（:8790）    │ │
│   │ 电池 ADC + 充电检测               │   │ microSD（表情/配置）   │ │
│   │ 急停（硬线，最高优先级）           │◄──┤ 硬线：E-STOP / 心跳   │ │
│   └──────────────────────────────────┘   └──────────────────────┘ │
│                                                                 │
│   2S 18650 ×2 (7.4V) ─┬─→ 电机 VM（直供）                        │
│                       └─→ MP1584 → 5V → Pi / ESP32 / 外设         │

> **没有摄像头。** 交互脑的外设只剩"屏幕 + 音频 + 网络"三样，
> 这三样都不需要持续编码大流量数据 —— 所以 Pi Zero 2W 的余量是够的，
> 也不需要为视频预留带宽和存储寿命。这与 §0.1 的第 2 条决定一致。

## 2. 关键选型论证（含被否掉的方案）

### 2.1 主控：ESP32-S3 + Pi Zero 2 W（双脑）

| 方案 | 结论 |
|---|---|
| ESP32-S3 单脑 | ❌ 屏幕+WiFi+音频会挤爆 PSRAM/CPU，运动环抖动 |
| 树莓派单脑 | ❌ Linux 调度抖动，电机闭环和急停不可靠；功耗大、启动慢 |
| 树莓派 Pico 2（RP2350） | ⚠ 双核 Cortex-M33，实时性比 ESP32 更好，但**没有 WiFi**，要再加模块 |
| **ESP32-S3 + Pi Zero 2 W** | ✅ **实时归实时、吞吐归吞吐**，各干各的 |

- **ESP32-S3-WROOM-1 N16R8**（16MB Flash / 8MB PSRAM）：双核 240MHz，
  PSRAM 够放音频缓冲；有 2 组 I2S、2 组 SPI、USB-OTG。
- **Pi Zero 2 W**：四核 A53 1GHz，跑得动圆形屏 60fps、音频和网关进程。
  功耗比 Pi 4/5 低得多（约 0.7–1.5W）。
  ⚠ 2024 年后 Pi Zero 2 W 供货和价格波动大，备选：Pi 3A+ / Pi 4B 2GB（更贵更费电）。
  **去掉摄像头之后**，Pi 的负载只剩"刷屏 + 音频 + 跑网关"，余量充足。

### 2.2 电机：N20 减速电机 + **霍尔编码器**（这是"高性能"的核心）

- 没有编码器 = 开环 = "给电转一秒"，**轮子打滑、电量变化、地面不同，走出来的距离全不一样**。
- 有编码器 = **闭环 PID** = "精确走 1.2 米"。这是这台机器人能不能真正好用的分水岭。
- 选型：N20 减速比 **1:100 ~ 1:150**，轮径 **34mm**（周长约 107mm）。
  - 目标速度 0.3 m/s → 轮轴约 168 rpm → 1:100 的 N20 在 6V 下够
  - 编码器 11 PPR × 4（正交）= 44 counts/电机圈；1:100 → 4400 counts/轮圈
  - → **约 0.024 mm/count**，精度远超需求
- ⚠ 具体减速比要按你买到的电机实测标定（空载转速、堵转扭矩）。

### 2.3 姿态：ICM-42688-P + 自写互补滤波

- **转向必须靠角度，不能靠时间。** "原地转 90°" 用延时是转不准的（电压、地面摩擦都在变）。
- ICM-42688-P：噪声低、零偏稳定，比 MPU6050 好一个档次。
- ⚠ 备选 **BNO085**（内置传感器融合，直接出欧拉角，省事但贵一倍、慢一些）。
  先用 MPU6050 打通也行，但**最终要做准角度就得上好的 IMU**。

### 2.4 避障与防跌落：**本地反射，不走网络**

- 前方 **VL53L0X ToF ×3**（左前/正前/右前）：2m 量程，I2C。
- **朝下防跌落红外 ×2**：桌面机器人**必须**有，否则一次失误就摔机。
- **反射逻辑跑在 ESP32 中断/高频轮询里**，响应 < 20ms，**不等 WiFi 往返**。
  这是"WiFi 断了机器人也不会冲下桌子"的根本保证。

### 2.5 交互脑上的外设

| 部件 | 选型 | 说明 |
|---|---|---|
| 屏幕 | **1.28" 圆形 IPS, GC9A01, 240×240, SPI** | 机器人表情的经典方案。⚠ 想更大可上 1.69"（ST7789V, 240×280），但功耗和排线都要重估 |
| 麦克风 | **ICS-43434 ×2**（I2S 数字） | 双麦可做简单波束成形/降噪；比 INMP441 噪声更低 |
| 功放 | **MAX98357A**（I2S 数字功放 3.2W）+ 4Ω3W 喇叭 | 无模拟走线，抗干扰 |
| 存储 | microSD 16GB（普通卡即可） | 只存表情资源、配置与本地日志。**不存视频**，所以不需要高耐久卡 |

> ✅ **已定：不装摄像头、不装录音存储。** 监控记录只有运动与事件日志（见 §11），
> 日志落在 PC 上的 `data/robot.db`，机器人本地不需要为录像准备任何存储。
>
> 📌 **圆屏挂在 Pi 上，不挂 ESP32-S3。** 所以表情的**渲染在 Pi 侧**
> （网关就跑在 Pi 上，情绪名直接交给本机渲染进程最短）。
> 协议里保留 `set_expr` 下行消息只是为了"万一有人把屏接到 ESP32 那侧"的接线选择，
> 默认不走。详见 `PROTOCOL.md` §6——那里原来写反了，已按本节改正。
>
> ⚠ **回声消除（AEC）**：机器人一边说话一边听，不做 AEC 就会把自己的声音当指令。
> Pi 上可以软件做（WebRTC AEC）。**建议先做"说完再听"的半双工规避** ——
> 那一行代码就能解决大部分自问自答，AEC 留到后面做优化。
> 去掉摄像头后 Pi 的 CPU 余量足够跑软件 AEC，所以这一步的风险比原构想低。

## 4. 电源与续航

**架构**：2S 18650（7.4V，2×2500mAh ≈ 18.5Wh）

- 电机 → **直供 7.4V**（TB6612 的 VM，最高 15V，效率高）
- 逻辑 → **MP1584EN 降压到 5V**（给 Pi、ESP32、ToF、IMU、屏）
- 电池电压 → 分压进 ESP32 ADC，**每 100ms 采样一次**

**功耗估算**

| 状态 | 功耗 | 续航 |
|---|---|---|
| 待机（屏幕亮 + WiFi + 监听） | ≈ 2.0 W | ≈ 9 h |
| 行驶（双电机正常速度） | ≈ 4.5 W | ≈ 4 h |
| 行驶 + 屏幕动效 + 语音 | ≈ 5.5 W | ≈ 3.4 h |

> 去掉摄像头与录像后，最费电的那一档（原 ≈7.0W，续航 2.6h）不存在了。
> 上表第三行是新的最坏情况。

**电池保护阈值**（必须硬编码，不能靠上层）

| 电压 | 动作 |
|---|---|
| > 7.4V | 正常 |
| < 6.8V（3.4V/cell） | 自动回充 |
| < 6.4V（3.2V/cell） | **立即停车**，禁止一切移动指令 |
| < 6.0V | 深度保护，断电 |

⚠ 2S 必须有**带均衡的保护板**；充电用 TP5100（2A）或充电桩内置充电器。
⚠ **充电时电机必须物理断电**（MOSFET 或继电器），不能只靠软件——一边充一边跑是事故。

## 5. 机械结构

- **轮系**：**差速驱动**（左右两个驱动轮）+ 前后各 1 个万向轮。
  差速的最大好处是**能原地转**，这对"回到充电桩"和"转头看人"都关键。
- **尺寸**：圆形底盘 ⌀120mm，总高约 95mm。
  - 电池放最底 → 重心低 → 不易翻
  - 屏幕在正面（面部），占主要视觉面积
  - 前缘：ToF ×3 + 防跌落 ×2
  - 后部：充电触点 ×2 + 万向轮
- **轮距** 90mm、轮径 34mm（这是后面运动学标定的基准）
- ⚠ **防跌落传感器的高度和角度必须实测**：太高会误判深色地毯，太低会在爬坡时误触发。

## 6. 引脚分配（ESP32-S3，⚠ 需按实际开发板核对）

| 功能 | GPIO | 备注 |
|---|---|---|
| 电机 PWM 左/右 | 4 / 5 | LEDC |
| 电机方向 左/右 | 6 / 7 | |
| 编码器 左 A/B | 15 / 16 | 中断 |
| 编码器 右 A/B | 17 / 18 | 中断 |
| TB6612 STBY | 21 | **拉低即切断电机输出**（急停用） |
| IMU / ToF I2C | 8 (SDA) / 9 (SCL) | ToF 用 XSHUT 分批改地址 |
| ToF XSHUT ×3 | 10 / 11 / 12 | |
| 防跌落 左/右 | 38 / 39 | 数字输入 |
| 电池 ADC | 1 | 分压后接入 |
| 充电检测 | 2 | 触点有电时为高 |
| 回充 IR 左/中/右 | 40 / 41 / 42 | |
| UART → Pi | 43 (TX) / 44 (RX) | 115200 8N1，NDJSON+CRC32 |
| **急停输入（硬线，来自 Pi）** | 3 | 来自 Pi 的一根线；低电平立即 STBY=0 + 刹车 |
| **物理急停按钮** | 3（同一根线） | **常闭开关接地**：按下即拉低。不经任何软件、不经 Pi |

> ⚠ 上表是**构想**。ESP32-S3 不同开发板可用 GPIO 不一样
> （尤其带 PSRAM 的模组会占用 33–37），**接线前必须对照你手上板子的引脚图**。
> 音频 I2S 走 Pi，不占 ESP32 引脚。
>
> **急停线的接法（重要）**：Pi 的 GPIO 与机身上的物理按钮**并联**到同一根急停线上，
> 两者任一拉低即停车。物理按钮用**常闭**接法：
> 按钮坏了/线断了 = 松开 = 拉低 = 停车。**失效方向是"停"，不是"继续跑"。**

### 7.1 蕴给机器人的 5 个接口（既有的，不要改）

网关**不碰**这五个；它们是"机器人（或别的程序）主动找蕴"的方向：

| 接口 | 用途 |
|---|---|
| `POST /api/chat` | 发一句话，返回文字 + 语音 |
| `GET /api/chat/stream?text=...` | 流式 SSE，反应更快 |
| `GET /api/events` | 长连接，**她会主动推消息**（机器人出故障时靠它告诉用户） |
| `POST /api/action` | 控制别的设备（**和网关的 `/action` 是两回事，别混**） |
| `GET /api/status` | 心跳探活 |

> ⚠ **命名撞车提醒**：蕴自己有 `POST /api/action`（蕴 → 别的东西），
> 网关有 `POST /action`（蕴 → 网关），`neko/devices.py` 的注释里
> 也把下游称为"网关"。读代码时认准**前缀**：`/api/` 是蕴的，`/robot/` 是网关的，
> 无前缀的 `/action` `/state` `/health` 是网关的（为了兼容 `tools/mock_gateway.py`）。

## 8. 安全设计（**这是重点，不是附录**）

物理世界的操作**没有读档**。下面每一条都要在固件里落实，不能只靠上层软件。

| # | 规则 | 为什么 | 落在哪 |
|---|---|---|---|
| 1 | **所有移动指令必须有界**（时长 ≤ 3s，速度 ≤ 70%） | 不存在"一直往前开"这种指令。想走更远就分几次发——累加距离**可审计**，"开到撞墙为止"不可审计 | 三处都挡：`neko/motion.py`、`robot/gateway/limits.py`、固件 `limits.h` |
| 2 | **急停走硬线**，不经过 UART 和 WiFi | 交互脑死机、网络堵塞时仍然能停 | ESP32 GPIO 中断 → 直接拉低 TB6612 **STBY** |
| 3 | **本地反射**：ToF/防跌落直接切断电机 | 不等网络往返，< 20ms | 固件中断/高频轮询，**不经过 UART** |
| 4 | **充电时物理断开电机** | 一边充一边跑是事故 | 硬件 MOSFET 断电 + 固件 `faults=["charging"]` 双保险 |
| 5 | **低压硬阈值停车** | 不能靠上层"记得检查电量" | 固件：<6.8V 自动回充 / <6.4V 立即停车禁动 / <6.0V 断电 |
| 6 | **上电自检**：编码器无脉冲、IMU 无响应 → 拒绝移动 | 传感器坏了却照常跑，等于盲开 | 固件自检 → `faults` 非空 → 网关拒绝一切移动 |
| 7 | **下发移动指令要 token** | 防止局域网里别的程序随手让它动 | 网关校验 `Authorization: Bearer`，只有 `/health` 免鉴权 |
| 8 | **同一时刻只放行一条移动命令** | 两条 `move` 同时下发时固件是"后者覆盖前者"，而两条 HTTP 都会收到成功——用户以为它俩都执行了 | 网关 `state.try_begin_cmd`（有测试） |
| 9 | **断链即安全**：网关/PC 掉线 → 2s 后自动停车 | 不靠心跳维持运动；**指令自带时长上限才是主保险**，心跳只是第二道 | 固件超时检测 + 指令有界 |
| 10 | **失败如实上报**，绝不假装成功 | 物理世界没有读档 | `ok:false` 必带 `reason`；`clamped` 必回传（静默截断是禁止的） |

**规则 1 的三处闸门必须同值**（70 / 3.0 / 3.0）。不一致就是 bug：
蕴以为 70、固件以为 100，用户会看到莫名其妙的行为。
网关侧**只允许更严**——配置文件里写 100 会被压回 70，因为固件的编译期常量是最后一道闸。

## 9. 分阶段落地与验收标准

每一阶段都要有**可测量的验收标准**，不然"做完了"没有意义。

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P0** | 单/双电机闭环 + IMU 定角 | 原地转 90°，**误差 < 3°**；直行 2m，**偏差 < 5cm** |
| **P1** | ToF 避障 + 防跌落 + 硬线急停 | 前方 20cm 障碍，**< 50ms 停车**；桌沿检测，**100% 不跌落**（连续 50 次） |
| **P2** | 双脑联通 + 表情屏 | UART 断线时实时脑进入安全停；表情 **≥ 30fps** |
| **P3** | 接入蕴（对话/指令） | 语音到动作 **端到端 < 2.5s**；指令识别正确率 > 90% |
| **P4** | 自动回充 | 从 1.5m 外任意角度，**一次对接成功率 > 80%**，失败能重试 |
| **P5** | 监控记录 | 事件与动作**全部落库**（含被拒绝的）；轨迹降采样后可画出"去过哪"；一键导出/清空生效；断电重启后记录不丢 |

**建议顺序**：P0 是地基，一定要先做扎实。**跳过 P0 直接做表情屏和回充，最后会返工。**

> 📌 **P0 到 P4 的运动与安全逻辑，现在就已经有可在 PC 上跑的验收了**：
> `robot/sim/` 是机器人模拟器，`robot/tests/` 里有真断言
> （原地转 90° 误差、直行 2m 偏差、防跌落、低压阈值、回充对接成功率）。
> 所以"必须先买硬件才能验证"这句话**只对机械与电气部分成立**，
> 算法部分现在就能验收，不必等采购。

## 10. 回充方案细节（最容易低估的一块）

**采用扫地机器人那套 IR 引导**：

```
充电桩：IR 发射器，向三个扇区发不同编码的信号（左 / 中 / 右）
机器人：三个 IR 接收管朝前扇形布置
```

**对接流程**：

1. **触发**：电量 < 6.8V / 定时 / 指令
2. **粗定位**：用里程计 + IMU 往记录的充电桩方向走（⚠ 里程计会漂，只能粗定位）
3. **搜索**：原地慢转，扫描 IR 信号；找不到就螺旋扩大搜索
4. **对准**：收到"中"区信号 → 正对；只收到"左/右" → 差速微调转向
5. **进站**：低速直行，直到**充电触点导通**（检测到充电电压）
6. **确认**：确认电流正常 → 停车 → **电机物理断电** → 灯/表情显示充电中
7. **失败处理**：3 次对不上 → 退回 50cm → 重试；连续失败 → 停在原地并**推消息给蕴**（让她告诉用户）

**⚠ 已知难点**
- **环境光干扰**：阳光里有大量红外，靠窗时 IR 引导会失灵。缓解：用 38kHz 调制 + 编码识别，不是简单的高低电平
- **充电桩位置必须固定且易于接近**（前面留出约 60cm 空旷）
- **触点接触**：弹簧针 + 自清洁斜角；反接保护二极管；限流电阻
- **对接时的防跌落**：充电桩边缘可能被防跌落传感器误判 → 进站流程里要临时降低其灵敏度或屏蔽（**但这会引入风险，需实测权衡**）

## 11. 监控记录与隐私（已定稿：**只记运动与事件，不装摄像头**）

### 11.1 记什么

| 表 | 内容 | 能不能查"它去过哪 / 为什么停了" |
|---|---|---|
| `robot_event` | 避障、防跌落、低压、对接各阶段、故障、模式切换、表情生效 | ✅ "为什么停了" |
| `robot_action` | 每一条下发的动作：谁发的、参数、成没成功、**被截断成什么** | ✅ "谁让它动的" |
| `robot_track` | 位姿轨迹，**降采样**（10s 一条，或航向变化 >5° 记一条） | ✅ "去过哪" |
| `robot_session` | 每次上下线的时段、时长、起止电量 | ✅ 使用规律 |

落在 PC 上的 `data/robot.db`（SQLite），由网关写。**机器人本地不存业务数据。**

**轨迹必须降采样**：20Hz 存一天是 172 万条，无法查询也无法维护；
10s 一条 → 一天约 8640 条，够画轨迹也能留一年。这个选择写在
`robot/gateway/storage.py` 的 `TrackSampler` 里，有测试覆盖。

### 11.2 保留策略

- 默认 **90 天**
- **`level=error` 的事件永久保留** —— 那是查"为什么出事"的唯一线索，
  不该因为放了三个月被自动删掉
- 一键导出（JSON，含 `Content-Disposition` 可直接下载）、一键清空（要显式确认）

### 11.3 隐私（去掉摄像头之后，这一节短了很多）

1. **没有摄像头、没有麦克风录音存储。** 所以不存在"被录下来"这件事
2. **急停两处可及**：PC 上点急停（`POST /robot/estop`）+ 机身物理按钮（常闭开关接硬线，
   拉低 TB6612 的 STBY）。**物理按钮不经任何软件**，程序死机也有效
3. **全部本地**：不接任何云。数据在 `data/robot.db`，要传给蕴也只在局域网
4. **工作指示 LED 是硬件**：机器人"正在运动/正在执行指令"时有独立 LED 指示，
   **不由屏幕代替** —— 屏幕卡住时人还得知道它在干活
5. 麦克风仍然用于对话，但**不落盘**：语音只用于当次识别

> 原构想里"放在家里、带摄像头和麦克风、还会自己移动的设备"这句话的顾虑，
> 在去掉摄像头后只剩下最后半句。剩下要守的就是第 2 条（急停必须物理可及）
> 和第 4 条（状态指示不能靠软件画出来）。

## 12. 风险清单

| 风险 | 影响 | 缓解 |
|---|---|---|
| 双脑 UART 协议复杂 | 调试成本高 | 已定：**NDJSON + CRC32**（不是定长帧）。理由见 `PROTOCOL.md` §2.1——串口上肉眼可读、加字段不破坏兼容。代价是解析开销，靠"控制环不解析 JSON"消除 |
| Pi Zero 2 W 供货/价格波动 | 成本失控 | 备选 Pi 3A+ / Pi 4B 2GB；⚠ 需重新算功耗和体积 |
| AEC 放哪边 | 自问自答 | 先做"说完再听"的**半双工**规避；去掉摄像头后 Pi 有余量跑软件 AEC |
| IR 回充受环境光影响 | 对接失败 | 38kHz 调制 + 编码识别（**不是简单高低电平**）；模拟器里已能注入环境光噪声来压这个风险 |
| 屏幕 30fps 吃 CPU | 表情卡顿 | 只重绘眼睛区域（局部刷新），不做全屏双缓冲 |
| 编码器标定依赖实物 | **P0 的真实精度无法提前确定** | 参数全做成编译期宏（`robot/firmware/core/limits.h` 一带），README 教你怎么实测填入。模拟器里的数字是**模型值**，不是你的电机实测值——这点必须分清 |
| 本机没有 C 编译器 | **固件未编译验证** | 见 `robot/firmware/README.md` 顶部的如实说明。运动算法已在 Python 模拟器里跑出真实数字作为对照 |
