# 蕴 · 猫娘伴友

**中文** | [English](README.en.md)

> **A local-first desktop companion: she chats with you, teaches herself from Bilibili,
> and can actually speak** — `edge-tts`, optionally re-voiced with RVC. → [English README](README.en.md)

一个装在你电脑上的猫娘伴友软件：**陪你聊天**、**自己去 B 站看视频学东西**、**把学到的讲给你听**、**能开口说话**。

名字和性格都可以改（`config.json` 里一行配置）。当前默认：**蕴**，清冷、理性、话不多但每句都在点上，称呼你为**同行者**。

> **MIT 许可，欢迎自取/改造。** 怎么装见[第一节](#一快速开始)；
> 哪些东西**故意没进仓库**（密钥、聊天记录、语音模型）见[第十一节](#十一开源与许可)。

> **这个仓库负责什么**
>
> 「蕴」本体：人设 / 记忆 / LLM / TTS / 界面 / **设备与运动的协议这一侧**。
> 机器人（固件、网关、仿真）是**另一套独立的东西**，通过 HTTP 协议跟这里对接 ——
> 所以本仓库只有协议与设备白名单，不含硬件驱动代码。
> 硬件选型与安全设计的想法记在 [`hardware/硬件构想.md`](hardware/硬件构想.md)。
>
> 为什么这样切：两套东西挤在同一个目录时，双方会同时改 `web/app.js`、`neko/brain.py`，
> 反复出现「文件已被修改」的互相覆盖，排查时也分不清某个改动是谁做的。
> **一个目录只归一个工作流写**，要跨界就走 HTTP 协议，不要直接改对方的文件。

## 一、快速开始

### 第 1 步：安装

双击 **`安装依赖.bat`**。

它会自动：找 Python → 建虚拟环境 → 装依赖（走国内镜像，约 1–3 分钟）→ 生成配置文件 → 跑一次自检。

### 第 2 步：填 API Key

**推荐直接在应用里填**：左侧「设置」→「大脑（大模型）」→ 粘贴 Key → 点「保存」。
保存后立刻生效、不用重启，输入框会自动清空（Key 不会留在页面上）。

也可以改配置文件 `config.json` 的 `llm.api_key`：

```json
{
  "llm": {
    "api_key": "sk-你的Key"
  }
}
```

> 改配置文件的话记得**保存**（编辑器里不按 Ctrl+S 磁盘上的文件不会变），
> 然后点设置页底部的「重新读取配置」。

Key 到 <https://platform.deepseek.com> 申请。也可以用系统环境变量 `DEEPSEEK_API_KEY`（优先级更高）。
**Key 只存在你本地，不会上传到任何地方。**

### 第 3 步：启动

**双击桌面上的「蕴 · 猫娘伴友」图标**（安装时会放一个快捷方式到桌面）。

也可以双击项目里的 **`启动蕴.vbs`** —— 无控制台窗口，直接出一个应用窗口。

> 出问题想看到日志，就用 **`启动蕴-控制台.bat`**；
> 无控制台模式下的日志会写到 `data\app.log`。

![界面预览](docs/界面预览.png)

仿微信的三栏布局：

- **最左（深色导航栏）**：她的头像（点一下就能换）+ 聊天 / 笔记 / 记忆 / 设置，带未读角标

不然每次都要重新点一遍。（想滚到某个小节就展开它：深链如 `#settings-bili`
在滚动前会先把那一节展开，不会让你对着一个收起的标题发愣。）

### 关于改文件的教训（维护者注意）


eko/learner.py 在 2026-10-04 **被一次误操作整份截断过**：一个用
str.find() 定位、带 if start == -1 兜底的删除脚本，锚点没匹配上时
end 变成 -1，切片 s[start:-1] 直接把 500 行删掉了 —— 而且因为剩下的
残file仍能通过 py_compile，**当场没有报错**。文件没有版本控制，
__pycache__ 里的 pyc 也被随后的编译覆盖，卷影副本不可用，**没有恢复源**，
最后是靠外部调用方的接口契约重写回来的。

三条教训：

1. **改文件不要用脚本做字符串切片删除**。要删就用 read/edit 工具，
   能看到前后文；脚本里的 ind() 一旦返回 -1，破坏力是整份文件。
2. **py_compile 通过 ≠ 文件完好**。残file也能编译。改完要跑
   	ools/selfcheck.py（10 项）和一次真实学习才算验证。
3. 这类项目**应该进版本控制**。这次没有任何恢复路径。

### 改了 web/ 界面没变？先怀疑浏览器缓存（维护者注意）

**现象**：改完 `web/index.html` / `app.js`，重启软件，窗口里还是旧界面 ——
看起来像"改动没同步"，但服务器端一切正常（`httpx` 拉一次就是新内容）。
**真正的原因**：这些静态响应以前只有 `ETag` / `Last-Modified`、**没有 `Cache-Control`**，
浏览器于是按"启发式缓存"自己算了个保鲜期，期间**根本不问服务器**，直接拿旧文件渲染。
重启软件没用（缓存属于浏览器配置目录 `data/browser_profile`，不属于进程）。

**怎么确认**：去 `data/browser_profile/Default/Cache/Cache_Data` 里按特征串搜，
能翻到那份旧文件（这次翻到的是一份 38KB、带 `<h3 class="sec" id="sec-rvc">` 的旧 index.html）。

**已经怎么修**：`neko/server.py` 里加了一层中间件，给 `/`、`/static/*`、`/favicon.ico`
统一回 `Cache-Control: no-cache` —— 不是"不缓存"，而是"每次用之前先问一句"：
没变就 304（很快），变了就拿新的。所以**以后改界面必定生效，不用清缓存**。

**验证要用真实窗口**：`tools/zz_app_window_check.py` 直接连正在运行的那个应用窗口
（需要带 `NEKOPAL_DEBUG_PORT=9222` 启动），检查它里面的 `app.js` 是不是新版、
折叠/开关这些新控件在不在 —— 另开一个浏览器验证是不够的，坑就出在那个窗口的缓存上。

### 关于脚本编码（维护者注意）

这三个启动脚本的编码是**故意选的**，不要随手改成 UTF-8：

- `启动蕴.vbs` → **UTF-16LE + BOM**。wscript 读 UTF-8 无 BOM 的 .vbs 会按 ANSI 解码，中文全乱。
- `启动蕴-静默.bat` → **纯 ASCII**。cmd 读取批处理文件时用的代码页在**启动那一刻就固定了**，运行中 `chcp` 改不了；只要文件里有非 ASCII 字节，换个控制台代码页就会解析出错。
- `安装依赖.bat` / `启动蕴-控制台.bat` → **GBK(936)**，配合中文 Windows 的默认控制台代码页。

另外 `.vbs` 里**故意不直接启动 pythonw**：`WScript.Shell.CurrentDirectory` 不保证传给子进程，而 pythonw 没有控制台，一旦 `-m neko.app` 找不到包就会**静默失败**（表现为"双击了但什么都没发生"）。所以它交给一个会显式 `cd` 的批处理。

## 五、配置说明

### 换人设

`config.json` → `persona`。当前是「蕴」：

```json
{
  "persona": {
    "name": "蕴",
    "call_user": "同行者",
    "style": "清冷智者",
    "keywords": ["清冷", "理性", "敏锐", "克制"],
    "meow": false,
    "custom_prompt": ""
  }
}
```

`style` 内置四套预设：

| 预设 | 性格 |
|---|---|
| **清冷智者** | 清冷、克制、理性，看得比你远但懒得说废话。**当前默认** |
| 软萌甜妹 | 软糯黏人，带「喵」口癖，会撒娇 |
| 温柔学姐 | 耐心可靠，鼓励式督促 |
| 毒舌傲娇 | 嘴硬心软，吐槽式督促 |

`custom_prompt` 是最高优先级的自由文本 —— 你想给她加什么设定就写什么。
改完重启应用生效。

### 换音色

**推荐直接试听**：左侧「设置」→「音色试听」→ 每个方案都有「试听」和「用这个」。
音色好不好听是主观的，我不替你决定，你听完再选。

当前默认（也是推荐的）：

```json
{
  "voice": {
    "azure_voice": "zh-CN-XiaoxiaoNeural",
    "rate": "+0%",
    "pitch_semitones": 2.0,
    "formant_shift": 0.12,
    "reverb": 0.0
  }
}
```

几个参数的实际含义（都是实测数据，不是猜的）：

| 参数 | 说明 |
|---|---|
| `azure_voice` | 底声。`Xiaoxiao`（Warm）比 `Xiaoyi`（Lively）低更稳，更贴「清冷」人设 |
| `pitch_semitones` | 音高。**这是最容易调坏的一项**：Xiaoyi +5 会把 F0 顶到 **393 Hz**，听起来像童声；Xiaoxiao +2 是 **264 Hz**，偏少女但自然 |
| `formant_shift` | 共鸣腔，正数偏细 |
| `rate` | 语速，原来的 `+8%` 偏赶，现在用 `+0%` |
| `reverb` | 默认 `0.0`，加混响容易有"罐头感" |
| `enabled: false` | 只出文字不出声（对应试听里的「完全不处理」） |

> 参考区间：**F0 240~280 Hz 是「偏少女但自然」**，超过 330 Hz 开始像童声。
> 想自己量：`.venv\Scripts\python.exe -c "import soundfile as sf,numpy as np;x,sr=sf.read(r'data\voice_cache\最新的.wav',dtype='float32');print(len(x)/sr, float(np.sqrt(np.mean(x**2))))"`

改完删掉 `data\voice_cache\` 里的缓存才会重新合成。

### 用训练好的真人模型变声（RVC）

上面那节调的是 edge-tts 的**底声 + DSP**；如果还不满意，可以再叠一层 **RVC**，
把合成好的声音丢给模型，换成"真人"的音色。

> **模型不随仓库分发。** `.pth` 权重是你自己准备/训练的，版权和使用范围由你负责
> （想做角色音色，请确认你对该音色有合法使用权）。仓库只提供"怎么接上去"的代码与配置。

| 举例音色 | 模型文件（自己填绝对路径） |
|---|---|
| 温柔御姐 | `<你的模型目录>\温柔御姐\wenrou.pth` |
| 温柔少女 | `<你的模型目录>\温柔少女\daboluo.pth` |
| 带索引的音色 | `<你的模型目录>\某音色\x.pth` + `x.index`（索引可选，加上相似度更高） |

**三层是串起来的**，顺序不能换：

```
edge-tts 出声  ->  猫娘 DSP（变调/共振峰）  ->  RVC 换成模型音色
```

**怎么用**：设置页 →「**声音**」小节 → 下面就是「RVC 变声（真人音色）」，
每个模型都有「试听」和「用这个」。试听走的是**和真实回复完全相同的链路**
（同一个 `NekoTTS`、同一套缓存规则），所以不会出现"试听好听、说话难听"这种对不上的情况。
同一小节里还有**声音总开关**：关掉她只出文字（不合成、不朗读，聊天页的「朗读」键也会收起来）。

**代价（必须知道，不然会以为软件卡死了）**：

| 项目 | 实测 |
|---|---|
| 单次推理 | 8 秒音频约 **6.4 秒**（0.8×）；**4.3 秒的短句要 5~6 秒**（固定开销占比高，约 1.2×） |
| 首次唤醒 | **约 3.8 秒**（起 RVC 自带的 Python 3.9 + import torch/librosa） |
| 换模型 | **0.3~0.4 秒**（首次从磁盘加载模型约 3.9 秒，之后常驻） |
| 一句话总耗时 | 4.3 秒的话：不变声 **2.7 秒** → 变声后 **7 秒左右** |

也就是说：**短句会明显变慢**。应用启动时会在后台把 worker 预热好，
所以只有"开机后第一句话"可能赶上唤醒时间。嫌慢就关开关，不用重启。

**为什么只能 CPU**：这台机器上 DirectML 会撞 `PrivateUse1` 调度错误，
`rmvpe` / `harvest` / `pm` 三个 f0 方法都试过，都不行 —— 所以 `f0_method` 用 `rmvpe`、设备是 CPU。

**配置在哪**（`config.json` → `voice.rvc`）：

```json
{
  "voice": {
    "rvc": {
      "enabled": true,
      "dir": "D:\\RVC\\RVC20240604AMD_Intel",
      "voice": "温柔御姐",
      "f0_method": "rmvpe",
      "timeout_sec": 120,
      "voices": [
        { "name": "温柔御姐", "model": "D:\\RVC\\models\\温柔御姐\\wenrou.pth", "pitch": 0 },
        { "name": "温柔少女", "model": "D:\\RVC\\models\\温柔少女\\daboluo.pth", "pitch": 0 },
        { "name": "带索引的音色", "model": "D:\\RVC\\models\\x\\x.pth",
          "index": "D:\\RVC\\models\\x\\added_IVF2672_Flat_nprobe_1_x.index", "pitch": 0 }
      ]
    }
  }
}
```

`dir` 指的是**RVC 整合包目录**（里面必须有 `runtime\python.exe`），
模型和 5.7GB 的运行时都在项目外面，所以这里存绝对路径。`pitch` 是每个音色单独的升降调补偿。

**五个坑（都真踩过，别再踩）**：

1. **变声失败必须静默退回原声。** 变声是锦上添花：它坏了顶多声音没变；
   但如果因此抛异常，整句话就没声音了。所以 `neko/tts.py` 里 RVC 那一层
   只返回成功/失败，绝不往外抛（见 `_apply_rvc`）。
2. **缓存键必须带上音色名。** 缓存的是"最终产物"（已经变声过的音频），
   不把音色算进 key 的话，点了「用这个」放出来的还是上一个音色的缓存。
3. **也不能"先写缓存再变声"。** 变声失败时如果原声已经落在"已变声"的缓存键上，
   这个键就**永久**返回没变声的音频 —— 之后把 RVC 修好了声音也不会变
   （现象很像"修了没用"，其实是被缓存骗了）。所以 `synth_to_cache`
   是"先写临时文件，变声成功才原子搬进缓存"。
4. **改这段配置要用递归合并。** `_patch_config` 只合并一层，
   用它写 `{"voice":{"rvc":{"voice":"x"}}}` 会把整个 `rvc` 段覆盖掉 ——
   三个模型的列表会被一次"换音色"顺手删掉。所以有 `_patch_config_deep`。
5. **别让 RVC 往自己安装目录里写 —— 受限环境下会写不进去。**
   RVC 启动时会改写 `configs/inuse/*.json`，还会让 numba 往
   site-packages 的 `__pycache__` 里写缓存。如果这个进程是**低完整性级别**
   （被沙箱降权的进程，例如由 Agent 拉起来的窗口），这两处都报 `PermissionError`；
   而 `os.access()` 会**谎报可写**，于是 numba 的重试循环会**占满一个核永不返回** ——
   表现就是"变声一直不出声，进程 CPU 100%"。绕法（见 `neko/rvc.py::spawn_env`）：
   - `NUMBA_CACHE_DIR` / `TEMP` / `TMP` 全部指到项目的 `data/` 下；
   - worker 的 cwd 用工作区里的 `data/rvc_home`（里面有一份 `configs/` 副本），
     让 RVC 的配置改写落在可写的地方；
   - `PATH` 里加上 RVC 根目录 —— `ffmpeg.exe` 就在那儿，而它是按相对路径
     `assets/hubert/hubert_base.pt` 找 hubert 的，所以**构造 `Config()` 和跑推理
     对 cwd 的要求正好相反**：前者在工作区，后者切回 RVC 根目录。

**怎么验它是真的生效了**（会真跑四个模型转换，几分钟）：

```bat
.venv\Scripts\python.exe tools\zz_rvc_e2e_test.py
```

它会把「不变声对照 + 三个模型」各合成一遍，打印时长/采样率/音量/F0 中位数，
并要求四份输出**两两都不相同** —— 相同就说明变声其实没生效。
另有 `tools\zz_rvc_debug.py`：手工跑一次转换并把 worker 的完整回包 + 日志打出来，
排查"到底是环境问题还是模型问题"时用它。

### 语气（让同一句话在不同情绪下听起来不一样）

问题：以前每条回复都用同一套 rate/pitch/volume 合成，所以
「太好了！我就知道你能行！」和「唉……算了，不想说了」听起来一模一样 ——
用户的原话是「声音没有语气的变化」。

**为什么只能用参数做**（三条路都实测过，别重复踩）：

1. **`mstts:express-as` 表现力风格 —— 不可用。**
   传 SSML 进去，edge-tts 会把它**转义成纯文本**，服务就去逐字朗读
   `<speak version="1.0" ...>` 这些标签了。证据：同一句话纯文本 0.3 秒，
   传 SSML 变 4.7 秒（长 15 倍），且 cheerful/sad/angry/gentle 四种风格时长几乎一样。
2. **换更会演的引擎**（GPT-SoVITS / CosyVoice）——需要 GPU 和几个 GB 下载，本机不现实。
3. **rate / pitch / volume —— 真实可用**（实测 rate ±20% 让时长 4.13s→3.46/5.16s；
   pitch ±30Hz 让 F0 从 221Hz 变 240/181Hz）。所以就在这三个参数上做文章。

**怎么做的**（`neko/prosody.py`）：

- **情绪从哪来**：优先用她回复里的 `[表情:xxx]` 标记 —— 那是模型自己给的情绪标签，
  比猜标点可靠得多。没有标记时再退回标点/关键词启发式。
- **逐句不同参数**：一条回复按中文标点拆成若干句，**每句单独合成再拼起来**：
  疑问句上扬（pitch +12Hz）、感叹句加快（rate +8%）、省略号收尾下沉（pitch −8Hz），
  相邻句子还做 ±6Hz 的交替偏移，避免每句一个调子。句间留 130ms 停顿。
- 句子超过 6 句就退回整条合成（否则要打十几次请求，而且碎句子拼接感明显）。

**实测效果**（同一条链路 `Brain.voice`）：

| 情绪 | 时长 | F0 中位 | 音量 |
|---|---|---|---|
| 生气 | 3.44s | **264 Hz** | 0.168 |
| 激动 | 4.44s | 258 Hz | 0.152 |
| 平静 | 3.73s | 238 Hz | 0.143 |
| 低落 | 5.07s | **200 Hz** | 0.149 |

最高与最低相差 **64 Hz**，耳朵能听出来。

代价：一句话拆几句就是几次 TTS 调用，一轮对话从约 4.5 秒变成约 5.5 秒。

> 注意顺序：情绪必须**先从带标记的原文**判定，再把标记剥掉送去合成。
> 反过来的话标记没了就没法判情绪 —— 而它正是最可靠的信号。

### 语音识别（没字幕就直接听视频的声音）

学习内容的来源现在有**五级降级**，`asr` 是新增的一级：

| 级 | 来源 | 是不是视频原话 |
|---|---|---|
| 1 | `subtitle` 字幕 | 是（UP 上传的字幕） |
| **2** | **`asr` 语音识别** | **是（机器转写，可能有同音字错）** |
| 3 | `audience` 弹幕 + 评论 | 否，是观众说的 |
| 4 | `desc` 只有简介 | 部分 |
| 5 | `title` 只有标题 | 否 |

`asr` 排在观众视角**之前**：它是视频里真实说的话，只是机器转写；弹幕评论是旁观者的二手转述。

**实测速度**（本机 16 核，int8 量化）：

| 模型 | 120 秒音频转写 | 速度比 | 20 分钟视频 |
|---|---|---|---|
| **base（默认）** | 4.5s | **26.5x 实时** | **0.8 分钟** |
| small | 12.4s | 9.7x 实时 | 2.1 分钟 |

base 快得多、准确度差距不大，所以默认 base。想更准改 `asr.model`。

**它真正解决的两个问题**（都是实测遇到的）：

1. **字幕错配时能救回来。** 有个高数视频的 CC 字幕是讲"大脑与 AI"的
   （B 站数据错配），而**语音识别出来的才是真正的高数内容**。
   所以「素材与标题不符」被判出来之后，会自动**跳过字幕改用语音识别重试**。
2. **只有非中文字幕时不再用错材料。** 遇到过一个中文视频只带一条
   **Español** 字幕 —— 拿它总结出来的东西没用。现在中文字幕优先，
   没有中文就改听声音。

**三个必须知道的环境坑**（都写在 `neko/asr.py` 里）：

- **音频是 M4A/AAC，`soundfile` 解不了**（它只支持 mp3/ogg/flac/wav），
  所以要装 **PyAV**（自带 ffmpeg 库，不用单独装 ffmpeg）。
- **`huggingface.co` 在本机不可达**，必须走 `hf-mirror.com`。
- **`huggingface_hub` 默认把缓存写 `~/.cache/huggingface`，本机被拒**（os error 5），
  还会因 xet 日志再报一次。所以要把 `HF_HOME` 指到项目内并关掉 xet ——
  这三个环境变量必须在 `import faster_whisper` **之前**设好。

依赖：`av` + `faster-whisper`（已在 `requirements.txt`）。
模型首次使用会自动下载到 `data/asr_models/`（base 约 145MB）。
配置在 `config.json` 的 `asr` 段：`enabled` / `model` / `max_seconds` / `language`。

> 任何一步失败（依赖没装、下载失败、识别不出内容）都会返回空并**继续往下降级**，
> 听不清不会把学习搞挂。

### 表情包为什么从"联网乱搜"改成了"B 站官方表情"

原来的做法是拿关键词去 Bing 搜图。问题是**搜到的图和当下情绪没有任何语义关联** ——
程序只会按关键词哈希在候选池里错开取，**图片内容是什么它根本不知道**。
结果就是用户收到过一张「××眼」（动漫里表示死了/昏过去）的表情，
配在她刚问完一个正经问题的后面，非常突兀。

B 站官方表情（`x/emote/user/panel/web`）完全不一样：

- **人工审核过**，不会出现不合时宜的内容；
- **每个都有文字标签**（呲牙 / 笑哭 / 星星眼 / 难过 / 生气 / 委屈 / 惊吓 / 思考 / 疑问…），
  标签天然能对上情绪 —— 选表情从"碰运气"变成**有依据的映射**；
- 走 B 站自己的 CDN，稳定、可外链。

实测（**登录后**）能拿到 4 个包共 **411 个**表情：小黄脸 225、热词系列 84、
tv_小电视 50、颜文字 52。13 种情绪的映射结果：

| 情绪 | 表情 | 情绪 | 表情 |
|---|---|---|---|
| happy | 呲牙 | sad | tv_难过 |
| laugh | 笑哭 | cry | 大哭 |
| love | 星星眼 | sleepy | tv_呆 |
| smug | tv_坏笑 | question | tv_疑问 |
| ok | OK | angry | tv_生气 |
| think | tv_思考 | surprise | tv_惊吓 |
| neutral | 微笑 | | |

> **这个接口必须登录**。未登录时返回 `code: -101`，一个都拿不到，
> 这时 `[表情:x]` 会被删掉（不会显示原始标记）。所以想让她发表情包，
> 得先在设置里扫码登录 B 站。

**踩过的坑**：`fetch_image` 原来固定带 `Referer: https://cn.bing.com/`，
而 **B 站 CDN 有防盗链** —— 带 bing 的 Referer 请求全部被拒，
表现是 `[表情:smug]` 整段被删掉、什么图都发不出来。现在按域名切换 Referer。

网络搜图那条路仍然保留（`[图片:搜索词]`），但提示词里已改成
**"只在真的想要某个具体画面时才用"**，因为它的贴合度没法保证。

界面上的用法：聊天输入框上方点 **😀 表情** →

- 「表情包」→ 点图**直接作为一条独立消息发出去**（和微信一样，不塞进输入框）；
  点右上角 `×` 删除；点「＋ 导入我的表情包」添加自己的
- 「颜文字」「Emoji」→ 点一下插到光标处

关于网络搜索的**实测结论**（写在 `neko/stickers.py` 里）：

- Giphy / Tenor：**这台机器连不上**（ConnectTimeout），境外 API 在此网络不可用

- **Bing 图片**（`cn.bing.com/images/async`）：可达，能稳定解出图片地址 —— 所以用它

#### 检索式必须补限定词（否则搜出来的不像猫娘）

一开始直接拿她的原词去搜，结果是：**「猫猫震惊」搜到相机拍的真猫照片，
「猫娘开心」搜到动漫壁纸**（700×700 到 2000×2000 的大图）。都不像表情包。

把几种检索式截图对比过（拼成对照图逐张看的）：

| 检索式 | 实际搜到 |
|---|---|
| `猫猫震惊` | 真猫照片（相机拍的） |
| `猫猫震惊 表情包` | 还是真猫照片，只是加了配字 |
| `猫娘 震惊 表情包 二次元` | 动漫猫娘，但多是全身立绘 |
| **`动漫猫娘 表情包 可爱 q版`** | **Q 版猫娘表情包，就是要的那种** |
| `猫娘 表情 可爱 动漫 免抠` | 插画裁切图 + 九宫格合集 |

所以 `build_query()` 会做三件事：

1. 补上前缀 `动漫猫娘 表情包 可爱 q版`（`stickers.search_prefix` 可改，设空则用原词）
2. 从她的关键词里**去掉「猫猫/猫咪/写真」这类词** —— 留着会把结果带向真猫照片
3. **硬排除**图库/新闻站（699pic、sinaimg、nximg… 以及 Bing 自己的缩略图缓存）。
   只降权是不够的：线上实测返回过一排 sinaimg/nximg 的照片，
   因为那一次结果清一色来自这些站，降权等于没降。池子不够时才回退使用。

#### 还有两个细节

- **不同关键词要给出不同的图**：前缀主导检索，Bing 对尾词（震惊/无语/开心）
  区分度很低，同一批热门图总排最前 —— 不错开的话她不管什么情绪都发同一张。
  所以按关键词哈希在候选池里错开取窗口。实测四个关键词结果**零重叠**。
- **不连发同一张**：最近发过的 URL 记在内存里（`_recent`，24 条），优先跳过。

这是网页抓取而不是官方 API，Bing 改版就可能失效。所以所有失败路径都是优雅降级：
搜不到就把标记删掉（不会让消息里出现 `[图片:xxx]` 这种原始标记），
网络不通时聊天照常。

> 她的人设提示词里有**你导入了哪些表情包**的清单，所以她只会发你有的那些。
> 一张都没导入时，提示词会明确让她不要写 `[表情:…]`，改用联网搜索。


### 清除聊天记录 / 清空数据

设置页最下面有「数据清理」：

| 按钮 | 影响范围 |
|---|---|
| 清除聊天记录 | 只删对话，笔记和记忆保留 |
| 清空长期记忆 | 她忘掉记住的关于你的事 |
| 删除全部学习笔记 | 看过的视频和知识点全删 |
| 全部清除 | 回到全新状态 |

**每个按钮都要点两次才会真的删**：第一次点击后**按钮自己**变成「再点一次确认」并变红闪烁
（原来提示写在最后一行的 `#clear-hint` 上，四个按钮分在四行 —— 点第一行的人
在下面第三行才看到提示，于是以为"这个键没作用"）。后端还要求请求里带
`confirm: "确认"`，少一个字就返回 400。

点「全部清除」时还会先把**具体要删多少**摆出来（对话 N 条 / 记忆 M 条 / 笔记 K 条）。

**清除之前会自动存一份档**（见下），所以清错了能读回来。

### 存档（类似游戏存档）

设置页的「存档」区：

- **保存当前进度** —— 起个名字（留空自动按时间命名），把**对话 / 记忆 / 笔记**整体存一份
- **存档列表** —— 每条显示时间、各类条数、文件大小，可 **跳转** / **删除**
- **跳转 = 切换存档槽，不覆盖当前进度**：跳转前会先把当前进度**写回它自己所属的槽位**，
  再切过去。所以来回跳不会丢东西。当前所在的存档会用绿框高亮并标「当前」。
  当前进度还没归属任何槽位时，会先给它建一个「我的进度」槽位收好。
- **自动存档：只有一个槽「当前进度」（`memory.auto_save` 可调）**

  | 时机 | 默认 | 说明 |
  |---|---|---|
  | `on_quit` 关闭程序 | **开** | 写进固定槽 `当前进度`，**滚动覆盖，永远只有一条** |
  | `on_start` 启动 | 关 | 启动不做存档（只做"续接"，见下） |
  | `before_clear` 清除前 | 关 | 关掉后**清除没有退路**，删了就真没了 |

- **关掉再打开 = 在原进度上继续**（游戏存档语义）

  启动时 `saves.resume()` 会把「当前进度」槽**续接**回来，而且**不新增任何存档条目**。
  但它不会无脑加载槽位 —— 上次若是**崩溃 / 被强杀**退出，根本没写成退出存档，
  实时库反而比槽位新，这时加载槽位会**丢掉新对话**。所以两边都看一眼，谁新用谁：

  | 情况 | 处理 |
  |---|---|
  | 实时库 ≥ 槽位 | 保留实时库，顺手把槽位同步过来（崩溃退出走这条） |
  | 实时库 < 槽位 | 用槽位恢复（库被清空/损坏了，槽位是最后一份好的）|

  两种情况都不丢东西。老版本的 `最近-退出` 会在启动时**自动改名**成 `当前进度`。

  ⚠ 关掉 `before_clear` 是个取舍：换来列表干净，代价是"全部清除"变得不可恢复。
  想重新打开这个保险，把 `config.json` 里 `memory.auto_save.before_clear` 设成 `true`。

  自动存档保留最近 20 份（`before_clear` 打开时是 5 份），手动存档不会被自动清理。

存在 `data/saves/`，一个存档就是一个 `.db` 文件，拷走就等于备份。

**为什么做这个**：用户反馈「关闭重开后会清除记录」。做了对照实验
（启动 → 聊天 → 关闭 → 重开，每步同时记录数据库和接口的条数）之后发现
**关闭重开本身不丢数据**，7 条消息完整活过了整个循环；真正抹掉数据的是
「全部清除」按钮被连着触发了三次，把对话、记忆、笔记一起清空了。
所以真正的解法是**给所有破坏性操作加退路**，而不是去修一个并不存在的持久化 bug。

> **踩过的坑（两个都很值得记）**
>
> **① 第一版存档是空壳。** 用 `sqlite3.Connection.backup()` 实现，
> 它会继承源库的 `journal_mode`（主库是 WAL），存档内容全落进
> `<名字>.db-wal` 附属文件；重新打开时没能恢复，读出来是 0 条 ——
> 列表上显示"9 条"，实际一条都读不回来。更糟的是我修它的时候
> 顺手把 `-wal` 当垃圾删了，**数据就真的没了**。
> 现在改成**把行导进一个用 rollback journal 新建的库**：结果就是一个干净的
> 单文件 `.db`。`data/saves/` 下只会有 `.db`、`.json` 和 `_active.txt`，
> 看到 `-wal`/`-shm` 就说明是旧版本留下的坏存档。
>
> **② 存档删不掉。** `list_saves()` 里写了 `with sqlite3.connect(p) as c:` ——
> **`with` 在 sqlite3 里只管事务，不关连接**。每列一次存档就泄漏一个
> **持有文件锁**的连接，于是删除时报
> `PermissionError: [WinError 32] 另一个程序正在使用此文件`。
> 这个坑 `memory.py` 里专门写过注释警告，我在新模块里又踩了一遍，
> 所以这次把它抽成了 `saves._conn()` 统一处理。

### 设备控制（接桌面机器人 / 智能家居）

> **轮式机器人的完整硬件构想见 [`hardware/硬件构想.md`](hardware/硬件构想.md)** ——
> 双脑架构、BOM、电源、引脚、回充流程、安全底线、分阶段验收标准。
> 运动协议已经在 `neko/motion.py` 里定好并做了限幅。

这一层是为"让蕴去控制别的设备"准备的。**默认关闭**。

#### 界面：设置页的「设备连接」

不用改 JSON，设置页里就能全部配好：

| 控件 | 作用 |
|---|---|
| **允许她操作设备** | 总开关。关着时她写 `[设备:...]` 会被静默删掉 |
| **允许局域网接入** | 默认只监听 `127.0.0.1`，硬件连不上。打开后 host 改成 `0.0.0.0`，**并自动生成访问 Token**，重启生效 |
| **设备网关地址** + 「测试连接」 | 网关连不连得上一键验，顺便把网关报的设备状态显示出来 |
| **可控设备（白名单）** | 列出/删除/添加设备，可标「危险·需确认」 |
| **机器人接入信息** | 局域网地址、访问 Token、5 个可用接口，一键「复制接入信息」 |

**为什么「局域网接入」和 Token 绑在一起**：只绑 `127.0.0.1` 谁都连不进来，
但硬件也连不上；一旦改成 `0.0.0.0` 而没有鉴权，**同一个 Wi-Fi 下任何人都能让她开锁**。
所以打开这个开关时会自动生成 token，并且服务端做了**只针对非本机来源**的校验：

- 本机（`127.0.0.1`）不受限 —— 界面自己就是这么连的，否则界面先挂了
- 局域网来的请求必须带 `Authorization: Bearer <token>` 或 `?token=`

#### 接入信息里给硬件的 5 个接口

| 接口 | 用途 |
|---|---|
| `POST /api/chat` | 发一句话，返回 `text` 和语音 `audio` |
| `GET /api/chat/stream?text=...` | 流式（SSE），机器人做即时反应更自然 |
| `GET /api/events` | SSE 长连接，**她会主动推消息**（学完东西想分享时） |
| `POST /api/action` | 控制设备 |
| `GET /api/status` | 状态探活，固件里做心跳用 |

#### 也可以直接改 config.json

```json
"devices": {
  "enabled": true,
  "gateway": "http://127.0.0.1:8791",
  "token": "",
  "list": [
    {"id": "desk_light", "name": "台灯", "kind": "light",
     "actions": {"开": "light.on", "关": "light.off"}, "dangerous": false},
    {"id": "door_lock", "name": "门锁", "kind": "lock",
     "actions": {"开": "lock.unlock", "关": "lock.lock"}, "dangerous": true}
  ]
}
```

打开后她的提示词里会列出这些设备，她写 `[设备:台灯=开]` 就会**真的去执行**
（沿用 `[学习:主题]` 那套"标记触发副作用"的范式）。

#### 架构：蕴是大脑，网关是手脚

```
蕴（PC，管人设/记忆/LLM/TTS）  --HTTP+Bearer-->  网关（MQTT/HTTP/串口/HA）--> 设备
```

蕴**不直接碰设备**，只把 `{device, action}` 交给网关。换设备、换协议都不用动大脑。
接口就一个：

```
POST /action  {"device": "desk_light", "action": "light.on"}
          ->  {"ok": true, "state": "on"}
```

仓库里带了个模拟网关 `tools/mock_gateway.py`，没有真硬件也能把整条链路跑通：

```
.venv\Scripts\python.exe tools\mock_gateway.py     # 监听 127.0.0.1:8791
```

#### 三道安全闸（物理世界没有"读档"）

1. **白名单**。只执行 `list` 里登记过的设备和动作。
   **LLM 一定会幻觉出不存在的设备**（"打开客厅的加湿器" —— 你根本没有加湿器），
   没登记的一律拒绝，并如实告诉她有哪些可用。
2. **危险动作二次确认**。`dangerous: true` 的动作**不直接执行**：先把待办挂起来，
   回复里说"我先不动手，你确认了我再执行"，等你说「确认」才真的下发；
   说「算了/取消」就撤销；说别的则继续挂着。走 `/api/action` 时必须在
   `confirm` 里回「确认」。
3. **审计**。每次动作（成功和失败都算）落 `actions` 表，`GET /api/actions` 可查。
   这是出问题时唯一能查的东西。

#### 相关接口

| 接口 | 用途 |
|---|---|
| `GET /api/devices` | 白名单 + 当前挂起的待办 |
| `POST /api/action` | 直接下发动作（机器人/脚本用），同样过白名单 |
| `GET /api/actions` | 审计日志 |

#### 实测（对着模拟网关跑的）

| 场景 | 结果 |
|---|---|
| `[设备:台灯=开]` | 网关状态 `off → on` ✅ |
| 聊天"帮我把台灯关掉" | 她回「（已执行：台灯 关）」，网关 `on → off` ✅ |
| 不存在的设备「加湿器」 | HTTP 400 + 可用设备列表 ✅ |
| 不存在的动作「起飞」 | HTTP 400 + 可用动作列表 ✅ |
| 门锁不带确认 | `need_confirm`，**门锁保持 locked** ✅ |
| 门锁带确认 / 说「确认」 | 执行，`unlocked` ✅ |
| 挂起后说「算了」 | 撤销，**门锁保持 locked** ✅ |

#### 接真实设备时的推荐选型

| 链路 | 推荐 | 理由 |
|---|---|---|
| 网关 ↔ 智能家居 | **HomeAssistant 当统一入口** | 米家/涂鸦/大多数品牌 HA 都已集成，只要跟 HA 的 REST/WebSocket 打交道，**不用为每个品牌写适配器** |
| 网关 ↔ ESP32 | **MQTT** | ESP32 上标配、断线重连成熟、**支持设备主动上报状态**（传感器/按钮），比 HTTP 轮询省电 |
| 机器人本体 ↔ 蕴 | **WebSocket** | 要传音频流 + 收事件推送。**音频别走 MQTT**（延迟和带宽不划算） |
| 唤醒词 | **本体本地做**（ESP-SR / openWakeWord） | 否则要 7×24 把麦克风音频传到 PC，费电又费流量 |

> **分界要清楚**：蕴是**大脑**（跑 PC，LLM 塞不进单片机），机器人是**身体**（一个客户端）。
> 机器人的麦克风 → 蕴的 ASR → LLM → 蕴的 TTS → 机器人的喇叭；
> 同时通过网关控制别的设备。

**还没做的**：语音唤醒/录音输入（`asr.py` 现在只吃 B 站音频流）、
设备状态回读（她目前不知道灯现在是开是关，问起来会靠上下文猜 ——
实测她说过"门现在敞着"而其实锁着）、带参数的动作（"亮度调到 60"）、
以及**本服务的鉴权**（现在只绑 127.0.0.1、无 token，
要开放给局域网内的机器人必须先加）。

### 用量与预算（看得见 + 拦得住）

聊天头部右上角一行灰字就是**蕴自己今天花掉的钱**，鼠标悬停看详情，点一下刷新。
**设置 → 用量与预算**里有开关和上限。

#### 显示的到底是"谁花的"（**这里踩过坑**）

| 口径 | 怎么算 | 用途 |
|---|---|---|
| **蕴自己**（主显示） | 每次调用返回的 `usage` token 数 × 单价 | 这才是"她花的钱" |
| 账户整体（参考） | 余额差（今日首次余额 − 当前余额） | 会把**同一个 key 在别处**的消耗也算进来 |

一开始主显示用的是**余额差**，结果用户反馈"其他地方使用额度也会并入其显示"——
实测同一时刻：**蕴自己 ¥0.0002，账户口径 ¥2.67**，差了一万多倍，
显示的根本不是她花的钱。现在改成按 token 估算。

为此给流式请求加了 `stream_options: {"include_usage": true}`（实测 DeepSeek 支持），
这样流式也能拿到 token 数，不用靠猜。单价在 `budget.price_in_*` 里，可自行改。

#### 每日额度：闸门必须下沉到 LLM 里（**这里也踩过坑**）

原来额度检查只写在两个聊天接口上，于是**额度用完之后**：

| 路径 | 之前 | 现在 |
|---|---|---|
| 聊天 `/api/chat`、`/api/chat/stream` | ✅ 拦得住 | ✅ |
| **学习总结** `learner.summarize()` | ❌ **照样调模型** | ✅ |
| **测验出题** `learner.quiz()` | ❌ **照样调模型** | ✅ |
| 定时自学的主动学习 | ❌ 走 summarize，照样烧 | ✅ |

用户反馈的"到达设定额度后没有进行措施"就是这个。
现在检查放在 `LLM._preflight()` 里 —— **任何调用路径都绕不过去**，
并且顺带把三种情况（没 key / 总开关关着 / 额度到顶）的提示语分清楚。

#### 四层防护

| 层 | 触发 | 效果 |
|---|---|---|
| 大模型总开关 | 手动关 | 零 API 调用 |
| 重复消息抑制 | 同一句话 10 分钟内第 4 次 | 不调模型 |
| 频率限制 | 每分钟 > 12 次 | 不调模型 |
| **每日额度** | 蕴自己今日估算 ≥ 上限 | **不调模型（全局生效）** |

### 按条删除聊天记录（右键 / 长按，仿微信）

「清除聊天记录」是**批量**。只想删掉某几条时：**在消息上右键**（或按住不放），弹出菜单：

| 菜单项 | 作用 |
|---|---|
| **复制** | 把这条的正文复制到剪贴板 |
| **多选** | 进入多选模式，点消息可多选，底部操作条批量删 |
| **删除** | 删掉这一条（**点两次**才真删） |

只删选中的，**其余原样保留** —— `POST /api/messages/delete {"ids":[...]}`。

> **删了就是删了。** 按条删除**不产生存档**（自动存档只保留"关闭程序时"那一种），
> 所以误删只能靠那次关闭前的存档兜底。这也是为什么「删除」要点两次
> （第一次变成红色的"确认删除"）。

**实现上的两个细节**：

1. **流式回复刚生成时前端不知道这条是几号。** 所以 `POST /api/chat/stream` 的
   `done` 事件会带上 `user_id` / `assistant_id`，前端挂到 DOM 的 `data-id` 上
   —— 否则刚聊完的那几条会删不掉。
2. **含表情包的回复在界面上是多个气泡、但同一条消息**，所以只有第一个气泡挂 id
   （删掉就是删掉整条）。

**长按**用 `pointerdown` + 550ms 计时 + 10px 位移阈值实现：按住不动才出菜单，
手指/鼠标一挪就取消，不会在滚动列表时误触发。

### 内置猫娘表情包（17 张）

表情包面板（输入框上方的 **😀 表情**）是**浮在聊天上的**，不占布局空间：
打开时聊天区高度**一点不变**（实测差 0px），不会把对话挤上去。
面板贴在输入区正上方，带阴影和圆角，内容多时自己滚（`max-height: 46vh`）。

> 以前它是普通流元素，一打开就把聊天区挤上去，用户反馈"不要压缩背景，改为覆盖"。
> 现在 `position: absolute; bottom: calc(100% + 6px)`，父级 `.composer` 做定位基准。

**点空白处就收起**：点消息区、点面板外的任何地方都收，按 `Esc` 也收。

> **点输入框那一块不收起** —— 和微信一样，你可能是想边打字边挑表情。

>

#### 这里踩过三次坑，都是"图和键对不上"

1. **最早走 Bing 搜图**：图和当下情绪**没有任何语义关联**（程序只按哈希错开取，
   根本不知道图里是什么）。用户收到过一张"××眼"配在正经问题后面。
2. **后来映射到 B 站官方表情**：标签是 `滑稽`/`辣眼睛`/`抠鼻`/`阴险` 这类
   **弹幕梗图**，跟"可爱猫娘"完全不是一回事，人设直接崩了。已彻底移除这条兜底
   —— 现在 key 不在本地库里就**直接丢掉标记**，不猜。
3. **键名和图片内容不一致**（最隐蔽的一次）：提示词里写着 `ok = 同意`、`question = 疑惑`，
   而实际图片是**「谢谢～」和「嫌弃～」**。她按情绪名挑，用户收到的就是一张
   **嫌弃脸配在正经提问后面** —— 这就是"表情包应用不恰当"的真正原因。

   **修法**：把每张图的名字改成它实际的内容（`question.png` → `disdain.png`），
   并且在提示词里**如实描述每张图长什么样**，因为**表情包图上有字，发出去等于她也说了那句话**。

#### 用多少才合适

提示词里给的是"**平均每 3~4 条回复发一次**"，并列出**绝对不发**的场合
（严肃/否定/纠错/拒绝/提醒风险、用户正经或情绪低落）。

> 这条尺度调过两次：一开始写"只要带情绪就发一个"→ 几乎每条都发；
> 修过之后写"多数回复不发才是正常的"→ **一条都不发**。
> 现在是给频率 + 列例外，实测 6 条发 2 次，且两张都和语境完全对得上。

#### 登录：扫码，不用给密码

点「扫码登录」→ 生成二维码 → **用对应 App 扫一下**。

- **不用把账号密码交给这个程序**，拿到的是 cookie，存在本地
- 随时可以在手机上「退出登录」让 cookie 失效，这里也可以点「退出登录」
- 二维码约 4 分钟过期，前端每 3 秒轮询一次，成功/过期都会提示

两家的登录流程**完全不同**：

- **网易云**：自己实现的 `weapi`（AES-128-CBC + RSA）→ `login/qrcode/unikey`
  → 轮询 `login/qrcode/client/login`（800 过期 / 801 待扫 / 802 待确认 / 803 成功）
- **QQ音乐**：QQ互联 `ptlogin` 那套 → `ptqrshow` 拿图 + `qrsig` →
  `ptqrtoken = hash33(qrsig)` → 轮询 `ptqrlogin`（65 过期 / 66 未扫 / 67 待确认 / 0 成功）
  → 跟着跳转把 `uin`/`qm_keyst` 收下来

#### ⚠ 手机扫码报"版本不匹配"的两个原因（都踩过）

**① 网易云：`type` 必须是 3，不是 1。**

```python
_post(cfg, "/weapi/login/qrcode/unikey", {"type": 3})   # 3 = 当前客户端
```

用 `type=1` 时**接口一切正常**（能拿到 unikey、轮询也返回 801），
只有手机 App 一扫才会报「版本不匹配」—— 因为那是旧客户端的二维码格式。
参考实现（`NeteaseCloudMusicApi` 的 `module/login_qr_key.js`）用的就是 `type: 3`。

**② 网易云：必须带一整套"设备 cookie"，而且 UA 是特定的那个。**

这是最隐蔽的一条。参考实现里 `util/request.js` 有两处关键：

```js
headers['User-Agent'] = options.ua || chooseUserAgent('weapi')
// weapi→pc 的 UA 是：Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ... Edg/124.0.0.0
```

```js
const processedCookie = {
  ...cookie, __remember_me: 'true', ntes_kaola_ad: '1',
  _ntes_nuid, _ntes_nnid, WNMCID, WEVNSM: '1.0.0',
  osver, deviceId, os: 'pc', channel: 'netease', appver: '3.1.17.204416',
}
```

少了这些，网易云会把请求当成**未知设备**，表现就是扫了码却被拒
（"请切换其他登录方式或升级新版本再试"）。我们是**首次生成后固定下来存进 kv**
—— 真机也不会每次换设备号。

**③ QQ音乐：`pt_3rd_aid` 必须是 QQ音乐自己的 `100497308`，不是 `0`。**

`pt_3rd_aid=0` 时 QQ 那边不知道是哪个应用在请求，手机一扫就是"版本不匹配 / 应用不存在"。
另外三个也容易错：

| 参数 | 错的 | 对的 |
|---|---|---|
| `t` | `time.time()`（时间戳） | **`random.random()`（0~1）** |
| `login_sig` | 空字符串 | **先 GET `xui.ptlogin2.qq.com/cgi-bin/xlogin` 拿 `pt_login_sig`** |
| 登录成功后 | 只收 cookie | 从返回里提 `uin` 和 refresh 地址，**再 GET 一次**（不跟随跳转） |

**④ QQ 的二维码「只有手机QQ App 认」——用别的扫会跳到 QQ 下载页**

把 `ptqrshow` 返回的图**解码出来**才看清：

```
http://txz.qq.com/p?k=zm0A7VkKEOntWQWjhtycLSM4lrtyRssh&f=716027609
```

`txz.qq.com` 是腾讯的下载页域名。这是 **QQ互联的登录码**，只有**手机QQ App 内置的
扫码器**会把它识别成"确认登录"；用微信、QQ音乐、系统相机去扫，都会被当成普通网址
打开，于是跳到 QQ 下载页。

**所以界面上的提示写死了要说清用哪个 App**（`hint` 里那段带 ⚠ 的文案）——
这种"看起来是 bug、其实是扫错 App"的情况，不把话说明白用户只会一直试。

> 解码验证用的 `opencv-python-headless` 只是**临时装来诊断**的，
> 进 requirements 太重（43MB），诊断完就卸了。

> 还要注意：`ptuiCB(...)` 的返回**结尾没有分号**，正则里写上 `;` 会让
> 所有状态都变成"未知"（`ptuiCB('66','0','','0','二维码未失效。', '')`）。

**排查手段**：两家的轮询遇到认不出的状态都会**把原始响应打进日志**
（`data/app.log`）。另外有一个**扫码轨迹**接口，只记状态**变化**
（801 → 802 → 803 这种），不打每一轮：

```
GET /api/music/qr/trace?provider=netease
-> {"trace": [{"ts":"08:54:00","code":801,"message":"等待扫码"},
              {"ts":"08:54:12","code":802,"message":"已扫码，请在手机上确认"},
              {"ts":"08:54:15","code":803,"message":"登录成功","detail":"拿到 cookie 字段：[...]"}]}
```

**如果轨迹里只有 801、从没出现 802**，说明手机 App **在本地就把二维码拒了** ——
服务器根本没收到扫码事件。这时问题不在我们的请求参数上，而在二维码本身。

**④ 扫码其实成功了，却被 `CookieConflict` 吃掉（最坑的一个）**

```python
got = dict(c.cookies.items())        # 这一行会在扫码成功那一刻抛异常
```

扫码成功时服务器会下发 `MUSIC_R_T` / `MUSIC_R_U`，而它们**同时落在多个域**
（`.music.163.com` 和 `music.163.com`）下。httpx 的 `Cookies.items()` 遇到
"多个同名 cookie"会抛 `CookieConflict`（它只吞 `KeyError`）——
于是**扫码明明成功、二维码却被消耗掉**，下一轮变成 800"已过期"，
用户看到的就是"扫了码但登录失败"，真正的错误信息被埋在一句 CookieConflict 里。

**`Cookies.get(name)` 同样会抛**（`get` 只吞 `KeyError`），所以 QQ 那边的
`c.cookies.get("qrsig")` 是同一个雷。现在统一改成直接翻 `cookies.jar` 并按名字去重：

```python
for ck in client.cookies.jar:
    out.setdefault(ck.name, ck.value)
```

> 教训：**只要看到"扫了没反应"，先去看轨迹里有没有 `-1 查询失败`** ——
> 那说明扫描事件到了，是我们自己处理崩了，不是二维码的问题。

#### 扫不动怎么办：直接导入 Cookie

**设置 → 音乐 → 扫不动？改用 Cookie 登录**。这条路**不依赖任何签名算法**，
只要能拿到 `MUSIC_U` 就能用：

1. 浏览器打开 `music.163.com` 并登录
2. `F12` → `Application` → `Cookies` → `https://music.163.com`
3. 找到 `MUSIC_U`，整段复制（或直接复制 `document.cookie`），粘进去

解析做得**很宽容**：整段 Cookie 头、devtools 的多行 `名字<Tab>值`、
带引号的 `document.cookie` 输出都能认。拿不到 `MUSIC_U` 会明确告诉你。

> **踩过的坑**：`me()` 原来是 ``return {"user_id": prof.get("userId"), ...}``，
> cookie 无效时网易云返回 `code:200` 但 `profile` 是空的，于是它返回
> ``{"user_id": None, ...}`` —— **非空字典恒为真**，假 cookie 也被判成"登录成功"。
> 现在没有 `userId` 一律返回 `{}`。

#### 听歌倾向（她"歌品差"的修复）

**问题**：搜「晴天 周杰伦」推的是《晴天(深情版)》by Lucky小爱 —— 一个翻唱。
原因是挑歌逻辑直接取 `hits[0]`，而网易云的搜索排序对**翻唱/改编版**很友好。

**修法：打分选歌**（`score_song`）。两条核心规则都是被实际结果教出来的：

- **标题命中比歌手命中重要得多。** 只按歌手匹配会推出《默》来
  （因为它歌手里有"周杰伦"），而用户搜的明明是《晴天》。
- **查询里有两个词、却一个都不在标题里 → 强扣分。** 那基本不是他要的那首。

另外：`翻唱/原唱/dj/remix/beat/钢琴版/…` 扣 30 分（`live/现场` 只扣 6，
现场版不算差但优先录音室版），用户标记过的**喜欢的歌手 +15**。

实测：

```
温柔 五月天   旧: 温柔/五月天      新: 温柔/五月天（32.0 分）   ✅ 原唱
成都 赵雷     旧: 成都/赵雷        新: 成都/赵雷（16.0 分）     ✅ 原唱
晴天 周杰伦   旧: 晴天(深情版)/Lucky小爱  新: 晴天/—（8.0 分，全是翻唱）
```

> 周杰伦那首**没有更好的结果了**：他的曲库不在网易云，搜出来全是翻唱。
> 打分能做的只是把最差的那些（`钢琴版[原唱:周杰伦]`、`PopxTrap Beat`）排到最后。

**倾向可以养**：

| 方式 | 效果 |
|---|---|
| 音乐页「听歌倾向」填歌手/风格 | 挑歌时加权/避开 |
| 「一起听过」每行的 👍 / 👎 | 把该歌手加进喜欢/不喜欢 |
| 「优先从最近在听里挑」 | 用你真实的播放记录当口味（比随机搜准得多）|

还有「她会挑哪首」按钮：给个关键词，**当场显示她按当前倾向会挑哪首**，
以及候选的打分排名 —— 调倾向时不用靠猜。

> **搜索必须节流 + 缓存。** 实测连着查几次就被网易云以
> `405 操作过于频繁` 挡掉，那时挑歌直接失败。现在同一关键词 10 分钟内复用缓存，
> 两次真实请求至少隔 1.2 秒，遇到 405 会退避重试一次。

#### 先问再讲（别一上来就长篇大论）

用户反馈"附加评论过多"。所以流程是：

1. 一起听 → **只说一句邀请 + 问一句**（实测 25 字：`同行者，一起听《晴天》吧～ 要我讲讲吗？`），
   同时把歌和歌词存进 `pending_music`
2. 用户点头 → 才展开讲（实测 127 字）

**"点头"的判定要严**：只有很短、很像应答的话才算（`好` `行` `讲讲` `展开说说` …）。
`好，那这个代码怎么改` / `那首歌不错` / `讲一下这个 bug` **都不算** ——
否则用户随口一句就会被灌一篇歌评。这条正则跑了 22 个用例（含 6 个否定用例）全对。

`pending_music` 有 15 分钟保质期，过期就不再追问。

「一起听过」列表可逐条删除（两击确认）。删掉记录**不影响**对话历史里那条消息。

#### 哪些行为会记进「一起听过」

| 来源 | 触发 | 列表里的标签 |
|---|---|---|
| `together` | 音乐页点「一起听一首」 | 一起听 |
| `share` | **她在聊天里主动分享**（`[音乐:歌名]`）| 她分享的 |

> **踩过的坑**：`share` 这条路径一开始**只发卡、不记录**，于是"她在聊天里推的歌"
> 在列表里是空的 —— 用户反馈"对话中分享的音乐没有记录在一起听中"。
> 现在两条路径都会落地成记录，分享那条还会把她当时说的话记成评论。

**短时间内的同歌同来源会并成一条**（`dedupe_sec`，默认 300 秒）。
实测用户会连点「一起听」—— 第一次要调模型生成邀请语（约十秒），等不及就再点一次，
于是同一个歌出现两条记录。现在会合并到同一条，并把更完整的评论换上去。
**不同来源不合并**：她"分享"一次、你"一起听"一次，是两件事。

前端也顺手改了：按钮进入 `在挑歌…` 状态并提示"约十秒"，免得让人以为没反应而重复点。

#### 接口是逆向的，所以坏掉也不能影响聊天

网易云的 weapi 是逆向接口，**它改签名或加风控就可能失效**。所以：

- 每个入口失败都只返回原因，**绝不把异常抛到界面上**
- 没登录时读「最近在听」返回友好提示，不是报错
- 「搜歌」其实**不需要登录**（`/weapi/search/get`）

> 另外实测 `/weapi/cloudsearch/get/web` 会返回 `50000005` 拿不到结果，
> 所以用的是 `/weapi/search/get`。

**为什么不直接用 NeteaseCloudMusicApi**：那是个 Node 服务，为了几个只读接口
在 Python 应用里再拖一个 Node 进程不划算。weapi 的算法（AES-128-CBC + RSA）
是公开且多年稳定的，自己实现只有几十行（`neko/music.py` 的 `_weapi`）。

**关于二维码为什么是 SVG**：网易云那张 PNG 要 Pillow，而环境里没有；为一个二维码去装
Pillow 不值得，所以改用 SVG（纯文本，前端直接塞进 DOM）。
QQ音乐那边 `ptqrshow` **直接返回图片**，base64 塞进 data URI 就行，两种都支持。

### 朗读开关会被记住（"莫名开启"的修复）

聊天页头部那个「朗读」勾选框，控制**回复时要不要自动念出来**。

**它现在存在 `config.json` 的 `voice.auto_read` 里**（`POST /api/voice/auto-read`），
`/api/status` 会带上这个值，界面加载时按它恢复。

> **踩过的坑**：这个勾选框以前只是 HTML 里写死的
> `<input type="checkbox" id="auto-voice" checked>`，**没有任何持久化** ——
> 于是每次加载都被拉回"开"。用户关了它，下次打开又自己开了，
> 看到的就是"朗读键总是莫名开启"。
>
> 对比一下旁边的「自学」：它一直是走后端配置 `schedule.auto_study` 同步的，
> 所以从来没这个毛病。**同一个界面上两个开关，一个持久化一个没有，
> 这就是最容易漏掉的那种不一致。**

**另一个坑（修的时候自己踩的）**：`e.currentTarget` **只在事件派发期间有效**，
`await` 过一次它就变成 `null`。所以监听器里要先把它存进局部变量：

```js
$("#auto-voice")?.addEventListener("change", async (e) => {
  const cb = e.currentTarget;   // ← 必须马上存下来
  ...
  await fetch(...);             // 过了这一行，e.currentTarget 就是 null 了
  cb.checked = !!d.auto_read;   // 用局部变量，不要再用 e.currentTarget
});
```

直接写 `e.currentTarget.checked = ...` 会抛
`Cannot set properties of null`，而且**不会中断已经发出去的那个请求** ——
设置其实存进去了，只是界面上的回显静默失败，很难察觉。

### 界面卡住不动 / 为什么不会再卡
聊天回复走 SSE 流。**如果后端的流卡住（连接还开着但不再发数据），
`onerror` 永远不会触发** —— 界面就一直停在"正在输入"，看起来像死了。三道保险：

1. **收尾一定会做。** 原来 `done` 分支里 `playAudio`/`renderText` 任意一处抛异常，
   后面的 `es.close()` 和 `finishTurn()` 就永远执行不到，`busy` 卡在 `true`。
   现在整段包在 `try/catch` + `settle()` 里，**收尾只做一次，但一定做**。
2. **卡死看门狗**：超过 **45 秒**没有 SSE 事件就强制收尾，并把那条标成
   「这条回复中断了 —— 后端超过 45 秒没动静」，而不是永远转圈。
3. **前端异常上报**：`window.onerror` / `unhandledrejection` / 渲染与放音的异常
   全部 POST 到 `/api/clientlog`。**排查这个 bug 时完全看不到抛了什么，只能靠猜** ——
   现在 `GET /api/clientlog` 就能看到。

后端也会在单轮回复超过 8 秒时打一行 `[chat] 这轮回复耗时 …`：
慢的通常不是大模型，而是标记后处理（`[学习:]` 会真的去学一遍，含 ASR 和网络请求）。

> **自检工具绝不能写生产数据。** `tools/selfcheck.py` 以前直接用真实配置建
> `Memory()` / `Brain()`，而 `b.reply("你好呀")` 走的是 `channel="local"`
> —— **正常聊天通道**。于是每跑一次自检，你的聊天里就多一条"你好呀"和她的回复，
> 记忆里还多一条"自检用的记忆条目"。跑了 14 次之后她开始数：
> 「第八次了喵」「第十二次了喵」「你是不是手滑给自己设了个定时器」，
> 而你完全不知道那些消息是自己冒出来的。
> 现在自检跑在 `data/selfcheck-xxxx/` 的**隔离临时库**上，结束自动删除。
> 顺带修了一处：本机 `TEMP` 指向项目内，`mkdtemp()` 会在仓库根目录留 `neko_selfcheck_*` 垃圾目录。

### 删单条笔记

`数据清理` 里的是**批量**删除。想只清掉某一条（比如某条学歪了的），用「笔记」页：

- **列表项右侧**：鼠标移上去会出现一个小小的 `×`，点一下直接删
- **笔记详情底部**：「删除这条笔记」按钮（同样要点两次）

两者都只删这条笔记，**不动对话记录、不动长期记忆** ——
`DELETE /api/notes/{bvid}`。清一条笔记却把聊天一起删掉是没道理的。

打开「笔记」页时会自动显示**最新那条**，不用先点一下才看到内容。
删数据这种事，误触的代价比多点一次大得多。

`subtitle_try` 是"最多试几个候选视频"。挑视频时有个实测得出的规则：
**搜索接口自带的弹幕数 `danmaku` 是"有没有观众材料"的可靠预测器** ——
实测 `danmaku = 0` 的视频，弹幕接口返回也是 0（不是抓取失败），
这类视频学下来只剩标题、等于白学，所以直接排除；然后在合理时长区间内优先挑弹幕多的。
这个规则不花任何额外请求。

### 换 AI 模型

设置 →「大脑（大模型）」，三步：

1. **服务商** —— 下拉选一个（DeepSeek / OpenAI / Kimi / 智谱 / 通义 / 硅基流动 / 本地 Ollama），
   会自动把接口地址填好。本项目的适配层统一走 `POST {base_url}/chat/completions`，
   所以**任何 OpenAI 兼容服务都能直接用**。
2. **获取可用模型** —— 点一下，程序会去问 `GET {base_url}/models`，
   把这个 Key **真正能用**的模型列出来。选一个就立刻切换。
3. **测一下能不能用** —— 真发一句话过去确认。

为什么要有第 2、3 步：

- 手打模型名很容易打错，而打错之后 `available()` 依然返回 True ——
  界面显示"已连接"，下一句聊天才报错，很难排查。列表是从接口拉回来的，不会错。
- 只看"有没有 Key"判断不了模型是否可用，所以第 3 步是**真的发一次请求**。

实测（本机 DeepSeek 账号）：

| 模型 | 探针结果 |
|---|---|
| deepseek-chat | ✔ 可用 |
| deepseek-v4-pro | ✔ 可用 |
| deepseek-flash | ✔ 可用 |

> 探针的 `max_tokens` 特意设成 64 而不是 16：有些模型会先输出思考内容，
> 给太小的话正式回复还没开始预算就用完了，看起来像"接口通了但没内容"。
> 真遇到这种空回复，界面会显示 ⚠ 提示而不是假装成功。
>
> 服务商预设里**刻意不写具体模型名**——模型会随服务商上下线变化，写死必然过期。
> 真实可用列表一律以「获取可用模型」拉回来的为准。

### 定时自学（她"自己会学"的关键）

```json
{
  "schedule": {
    "auto_study": true,
    "times": ["12:30", "21:00"],
    "every_hours": 4,
    "catch_up": true,
    "startup_delay": 120
  }
}
```

界面上有两个地方能开关自学：

| 位置 | 用途 |
|---|---|
| **聊天窗口顶部**「自学」开关 | 日常随手开关，和「朗读」并排，一眼能看到当前是否开着 |
| 设置 →「自主学习」 | 详细配置：固定时刻、间隔小时、启动补学 |

两处改的是同一个设置，会互相同步。切换失败时开关会自动回滚，不会出现
"开关显示开着、实际没开"骗人的状态。

**三种触发方式**，为什么需要三种：

| 方式 | 说明 |
|---|---|
| 固定时刻 `times` | 每天到点学一次（带同刻去重，同一天同一时刻只触发一次） |
| **间隔模式** `every_hours` | 软件运行期间每隔 N 小时学一次；`0` = 关闭 |
| **启动补学** `catch_up` | 启动后延迟 `startup_delay` 秒，如果今天还没学过就补一次 |

只有固定时刻是不够的——**那个时间点你没开着软件，今天就等于没学**，
用户看到的正是"她从来不自己学"。上面两种方式就是补这个洞的。

启动补学的"今天学过没"是**记在数据库里的**（`kv.last_study_date`），
不是记在内存里：否则每重启一次软件她就补学一次，白白吃掉每日上限
（`bilibili.daily_limit`）。

到点她会自己去学一个视频，学完通过实时通道**主动推到你聊天窗口里**
（就算应用当时没开，笔记也落了库，下次打开能看到）。

> **登录 B 站后这一步的产出会明显变好**：`level` 会从 `audience`（观众视角）
> 变成 `subtitle`（有字幕），`confidence` 从 `medium` 升到 `high`，
> 笔记内容也从"观众在讨论什么"变成"视频原话讲了什么"。实测对比见
> `docs/` 或直接看笔记列表上的徽章。

## 六、已知边界（不吹）

| 项 | 实际情况 |
|---|---|
| **B 站字幕** | **实测：未登录拿不到。** `player/v2` 返回 `code:0`，但 `subtitles` 为空、`ai_subtitles` 是 `null` —— B 站把字幕设成了登录门槛功能。抽样 145 个视频，**0 个有字幕** |
| **观众视角（关键补救）** | 字幕拿不到时改用**弹幕 + 评论区**：这两个源免登录开放，而且常有人复述知识点、纠正 UP 主。实测一个零字幕视频抠出 **6425 字**有效材料（`range` 原理、字典键必须可哈希、`sort` vs `sorted`、带时间戳的完整提纲）。她**会如实说明"这是观众说的"**，不会假装是视频原话 |
| **四级内容降级** | `字幕 → 观众视角 → 简介+分P → 只有标题`。每一级都在界面上有徽章标注 |
| **B 站搜索** | 需要 WBI 签名，已实测跑通。**最脆弱的一环其实是 `buvid3` Cookie**（缺了会 412），不是签名本身 |
| **猫娘音色** | 纯 CPU DSP 只能做到**偏甜偏年轻的少女音**，不是动漫猫娘音。当前配置实测 F0 **264 Hz**（自然区间 240–280 Hz）。之前用 Xiaoyi +5 会顶到 393 Hz、听起来像童声，已修正。要真猫娘音得换音源（GPT-SoVITS / Bert-VITS2 挂角色音色模型） |
| **语音自动播放** | 浏览器（含 Edge 应用窗口）会拦下"用户还没交互就自动播放"的音频。被拦下时消息里会出现一个「🔊 点这里播放语音」按钮，而不是静默没声音 |
| **网络表情包** | 走必应图片搜索（网页抓取，非官方 API），连不上或改版时会自动降级，不会让聊天出错 |
| **语音速度** | 实测约 **2.4–3.1 倍速**（12 秒语音约 4–5 秒处理），缓存命中近乎瞬时。首次调用有约 4 秒冷启动 |
| **mp3 解码** | 不需要 ffmpeg：`soundfile` 捆绑的 libsndfile 自带 MP3 解码（所以要求 `soundfile>=0.13`） |
| **长期记忆** | 中文二元组关键词检索，不是向量检索。几千条以内够用 |
| **语音输入** | 这一版只做**语音输出**，还不能你说话给她听 |
| **窗口后端** | 优先 pywebview 原生窗口；但 **pythonnet 目前不支持 Python 3.14**，所以本机走 Edge 的 `--app` 无边框应用窗口（无地址栏、无标签页、独立任务栏图标、独立浏览器配置目录）。换到 3.12 环境会自动升级为原生窗口 |
| **为什么要关沙箱** | 实测在这台机器的会话里，Chromium 的渲染进程沙箱初始化失败（Edge 日志里能看到注册表访问被拒），结果是**窗口一片空白、什么都不显示**。加 `--no-sandbox` 后页面才正常渲染。因为窗口只加载 `127.0.0.1` 上我们自己进程提供的页面、不加载任何外部内容，所以这个取舍可接受。想恢复沙箱：`config.json` 里 `window.disable_sandbox` 设 `false`（或设环境变量 `NEKOPAL_DISABLE_SANDBOX=0`）。附带用 `--test-type` 抑制了 Edge 那条"不受支持的命令行标志"提示条 |

## 七、怎么确认它真的能跑

两个自检脚本，**都不需要先配 API Key**：

```powershell
# 1) 单元自检：依赖 / 配置 / 记忆库 / 人设 / 大脑 / B站 / 观众素材 / 调度器 / 语音 / 服务
.venv\Scripts\python.exe tools\selfcheck.py

# 2) 端到端验证：用本地模拟模型把完整链路真跑一遍
.venv\Scripts\python.exe tools\e2e_check.py

# 3) 界面行为验证：真的去点（折叠键 / 试听按钮 / 声音总开关），需要软件正在运行
.venv\Scripts\python.exe tools\zz_ui_check.py
```

`zz_ui_check.py` 用本机 Edge 的 DevTools 协议**在页面里真点**：
折叠键能不能展开收起、「声音」小节里是不是真装着音色试听和 RVC、
展开之后「试听」按钮还能不能用、声音总开关关掉后对话页的「朗读」键是不是真的消失。
为什么要它：这些坏法**截图上看不出来** —— 比如折叠时如果把节点重写一遍，
监听器会全丢，按钮就变成点不动的摆设，而静态截图里它长得完全正常。
（项目里没有 websocket 库，所以这个脚本自带一个最小 WebSocket 客户端。）

`e2e_check.py` 会在本地起一个说 OpenAI 协议的模拟模型（`tools/mock_llm.py`），
把大脑指向它、用临时数据库，走一遍：
**流式聊天 → 学一个真实 B 站视频 → 提炼知识点 → 存笔记 → 出题 → 对答案 → 记忆检索 → 指令 → 无 Key 降级**。

关键在于那个模拟模型**不是返回死数据**，而是从收到的 prompt 里派生回答。
所以"4/4 个知识点都能在材料里溯源"这条断言，等价于证明了
**真实 B 站材料确实进入了模型上下文** —— 而不是只看日志像不像。

当前实测：单元自检 10/10，端到端 11/11（连跑 3 次稳定）。

还有一个**界面是否真的渲染出来**的判据，写在状态里：

```powershell
.venv\Scripts\python.exe -c "import httpx,json;print(json.loads(httpx.get('http://127.0.0.1:8790/api/status').text)['status']['ui_connected'])"
```

`ui_connected` 为 `true` 表示界面已经加载成功并建立了实时连接。
这是唯一能区分"服务正常"和"窗口真的画出来了"的信号 ——
光看 HTTP 200 是不够的，窗口曾经在服务完全正常的情况下白屏过。

**依赖装不上（提示连接超时）**
直连 pypi.org 在国内经常超时。换镜像：

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt --no-cache-dir -i https://mirrors.aliyun.com/pypi/simple
```

**端口被占**
改 `config.json` 里 `server.port`，或 `.venv\Scripts\python.exe -m neko.app --port 8899`。

## 九、为什么没有做微信接入

最初的方向是让她住进微信。走到一半发现两个绕不过去的问题，所以**改成了独立软件**：

1. `wxauto4`（免费版）要求微信客户端 **≤ 4.1.8.107**，而当时那台机器上装的是 **4.1.13.65**；同时它要求 Python **3.9–3.12**，而开发环境只有 3.14。两个版本号都不在支持范围内。
2. 降级虽然可行（安装包找得到，SHA256 三方一致），但**装上去能不能登录完全没验证过** —— 腾讯可能直接提示"版本过低"。而且那要卸载正在用的微信（`xwechat_files` 实测 0.72 GiB / 3191 文件），风险不对称。

完整调研（含下载源实测、降级步骤、替代方案对比）保留在 **[docs/调研-微信接入可行性.md](docs/调研-微信接入可行性.md)**，如果你以后还想走这条路，那份报告是现成的。

### 哪些东西**不在**仓库里（都是故意的）

| 不在仓库 | 为什么 | 你要怎么做 |
|---|---|---|
| `config.json` | 里面有你的 API Key、B 站 Cookie、设备网关 token | 从 `config.example.json` 生成；`.gitignore` 已经挡住它 |
| `data/` | 聊天记录、记忆库、语音缓存、浏览器配置（含登录态）、ASR 模型 | 首次运行自动生成 |
| RVC 模型 `.pth` / `.index` | 体积大，而且多半有版权 | 自己准备，在设置页「声音」里填路径 |
| `VoiceChanger`（猫娘 DSP 的来源） | 它是**另一个独立项目**，本仓库只是复用了它的 DSP 链 | 可选：放到本项目的同级目录，或设 `NEKO_VOICECHANGER_ROOT` 指过去。**没有它也能跑**，只是少一层音色处理 |
| 表情包图片 | 每人导入的不一样，且多为他人作品 | 自己丢进 `data/stickers/` |

> ⚠️ **提交前检查一遍**：`git status` 里不该出现 `config.json`。
> 一旦带着密钥 push 出去，**历史里就永久留着**，只能吊销 Key 了事。
